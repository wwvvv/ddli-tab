# DTab 简化收费方案与 New API 接入边界

版本：1.0 · 确认日期：2026-09-16 · 状态：已确认的产品规则，尚未实现或启用收费

关联：[PRD](01-PRD.md) · [技术架构](02-ARCHITECTURE.md) · [实施任务](05-CODEX-TASKS.md) · [原始上线门槛](04-AUDIT.md)

## 1. 唯一的初期收费口径

DTab 免费使用；只有一个付费等级，名称为 **DTab 会员**。会员解锁已列明的会员工具/高级功能，并获得更多每日积分。AI 与明确按次产生费用的处理消耗积分；普通用户和会员都能购买积分包。

月付、年付只是同一会员的有效期/购买选项，不是不同等级。是否首发年付与具体售价须在上线前确认，不能预售尚不可用的功能。

本文件取代历史讨论中的 Free/Pro/Max 多档套餐、多应用 VIP、月度积分池、每日累积/体力恢复、任务签到奖励、首购第三钱包、主题/小工具单品买断等初期方案。既有文档中的技术术语 Product、Entitlement 不代表必须销售单品。

| 用户侧概念 | 含义 | 初期出售什么 |
| --- | --- | --- |
| 免费使用 | 基础桌面、网址、自定义布局、基础内容；登录后可使用少量每日 AI 积分 | 不收费 |
| DTab 会员 | 会员工具/高级功能 + 更多每日积分 | 一个会员，按确认的期限销售 |
| 积分 | 支付已明确标注的 AI/付费接口处理 | 少量固定规格的积分包 |

不做 Max，不做每应用会员，不把普通小工具每次点击计费，不开放用积分兑换主题/会员/商品、转账或提现。未来改变这些边界须另立决策，不在本次实施时预建平台经济系统。

## 2. 按功能成本分类，不按应用名称收费

| 功能类别 | 普通用户 | 会员 | 积分规则 |
| --- | --- | --- | --- |
| 基础桌面、网址、基础主题/组件 | 免费 | 免费 | 不扣积分 |
| 普通会员工具，额外处理成本很低 | 可配置少量体验；不强制每个工具都有独立次数系统 | 包含在会员中 | 不扣积分 |
| AI 或有明确按次成本的第三方 API 操作 | 在功能可用、身份与余额满足时使用 | 使用，每日积分更多 | 两类用户都按公示规则消耗积分 |
| 特别高成本的批量/长视频处理 | 仅在服务能力与限制已验收时开放 | 同样受公开的大小/时长/并发限制 | 不能因为开会员就宣传无限算力 |

“工具看会员，AI 看积分”只是概括。非 AI 的收费 API 同样可能需要积分；本地运行的 AI/算法也不必强制按次扣分。不得为了统一口号对低成本功能额外扣费。

### 2.1 去水印的示例合同

只针对用户自有或获授权处理的素材定义产品，不在本次实现去水印引擎。

- 普通模式：本地算法或已确认成本很低，普通用户可有少量体验，会员使用时显示“已包含在会员中”，不扣积分。
- 智能修复：调用付费模型/API，生成前显示“预计使用 N 积分”。N 来自真实参数与已发布规则，不在文档写死固定价格。
- 批量/长视频：先明确可处理的体积、时长和并发；成本较高的操作走积分，不能在结果生成后突然加付费下载门槛。
- 免费体验次数不是积分余额。若要跨设备可靠限制次数，在对应服务端计数；纯本地次数只能作为体验限制，不能宣称强防绕过。

### 2.2 大型 AI 应用

AI Studio 等大型应用的基础工作区原则上允许已登录用户进入，会员可解锁高级工作流、批量等明确功能。AI 生成使用积分，普通用户可以单独购买积分使用可用的生成能力，不要求先买会员再买积分。

统一经 DTab 登录/授权，不等于所有应用必须先付费。关闭/移除桌面入口不撤销购买积分；会员到期不删除个人项目、照片或导出能力。

## 3. 积分规则：一个单位，两个来源

### 3.1 每日积分

- 普通已登录用户获得较少额度，会员获得较多额度；具体数值未定。
- 每日重置为该用户等级对应额度，不累计、不结转、不要求手动签到。
- 未登录游客仍可用基础桌面；不发放可匿名消耗付费模型的每日额度。
- 未使用的每日额度到周期结束失效，不转入购买积分，不允许囤积。
- 重置时间必须明确展示。产品默认目标为每日 00:00（UTC+08:00，统一业务时区）；上线前固定服务端时区并核验实际 next_reset_at。不能依赖设备时区、前端倒计时或登录次数刷新额度。

New API 的 daily 是待配置并验收的实现方式，不是 DTab 每日再往钱包充值一次。禁止“订阅重置 + DTab cron 加币”双重发放。

### 3.2 购买积分

- 不参与每日重置，不因会员到期或取消续费清零；普通用户也可购买。
- 初期不设置日常自动过期，不宣传无法保证的“终身云服务”。服务终止、退款等处理必须在购买前说明并满足实际运营要求。
- 购买是用户主动确认的交易。自动充值、余额不足自动买包、自动启用支付扣款均默认关闭。
- 本期不混入不同期限的签到、邀请、新人奖励，避免出现第三种消费池和复杂优先级。

### 3.3 扣除顺序与展示

产品目标：先用每日积分，不足部分再用已购买积分。首次将消耗购买积分、高额操作或预计费用明显上升时明确提示；低成本正常操作不逐条弹窗，但可查明细。

**不能把 New API“钱包回退”直接宣称为已支持一笔请求跨池按差额拆扣。**上线前验证剩余每日额度小于单次预扣、最终实际费用大于预扣、多订阅、跨日完成等情况。若当前版本只支持整笔回退钱包，应保持该扣费路径未开放，评估受支持配置或最小上游补丁；不得展示“只扣差额”而实际扣整笔，也不新建第二套独立扣费账本补洞。

设置页建议显示：

```text
积分
今日可用：{daily_remaining} / {daily_total}
购买积分：{purchased_remaining}
每日 {next_reset_time} 重置今日积分，购买积分不受影响
[积分明细]  [购买积分]
```

首页可简写“积分”，详情必须能区分来源。后端无法确认余额时显示“暂时无法获取”，不能用缓存值保证可消费，不能将多个并发请求各自看到的余额当作预扣。

### 3.4 会员购买、续期与到期

会员开通和积分包发放的金额、期限、每日额度、兑换比例、税费与退款规则均为待确认参数，不沿用历史聊天中的示例价格。

续期延长同一会员有效期，不让多次购买叠出多个每日积分池。普通用户转会员的当日，目标是补足额度差额、保留当日已经消费的量，而不是重复发一份完整额度；反复开关会员/重复支付回调不能刷积分。具体跨日、退款与降级规则须在计费验证中落实，不向生产直接写数据库猜测。

取消自动续费只停止下期收费，不应立刻撤销已付费期限。本期默认手动续购；后续有自动续费时单独增加明确授权。退款、封禁等导致权益即时撤销必须走对应流程并留审计记录，不能与普通取消续费混为一个动作。

## 4. 用户界面与费用透明

会员页只对比“免费使用”和“DTab 会员”。工具详情展示“免费”或“会员包含”，可按具体操作补充“部分处理使用积分”；初期没有单品购买按钮或 Max 升级入口。

| 操作 | 用户看到的说明 |
| --- | --- |
| 会员内普通工具 | 已包含在会员中 → 开始处理 |
| 已确认固定价格的操作 | 使用 N 积分 → 生成 |
| 变量成本的图像/视频处理 | 预计 N 积分，注明影响因素/已授权上限 |
| 对话/Agent 等多轮任务 | 普通聊天不刷屏扣费通知；高成本或长任务有预算上限和结束明细 |
| 额度不足 | 等待下一次每日重置，或主动购买积分；不以后台自动充值继续 |

固定价、估算价、预留上限、实际结算是不同字段。没有可靠报价能力不能将“估算”标为固定承诺。不得在 DTab 写一张价格表、New API 再用另一张表扣费；报价必须与网关所用计费规则版本一致。

如果支持用户自选具体模型，不可因后台成本变化偷偷替换成另一个模型。只有明确选“自动”的操作可以按公示策略路由；报价变化超过已确认范围应在提交前重新确认。不能用隐藏限额或静默降质取代成本管理。

所有额度与交易页面仍服从设计系统的字体/弹层/响应式规范；“简单”不能删除到期说明、积分来源、失败状态和费用提示。

## 5. New API 与 DTab 的权威边界

**默认复用原版 New API + DTab 服务端适配层；先做验证，不立即 Fork。**

| 能力 | 权威系统 | DTab 需要做什么 |
| --- | --- | --- |
| 身份、统一注册/登录 | DTab / Supabase Auth | 维护稳定 user_id 与外部应用身份映射 |
| 会员商品、订单、付款、退款与平台权益 | DTab | 一个收银台，不把网关充值页面开放给最终用户 |
| 每日 AI 周期额度、购买 AI 配额、预扣/结算/退款 | New API | 映射、读取、展示与核对，不另建 AI 可用余额真源 |
| 模型、渠道、路由、计价规则 | New API | 返回经验证的模型/操作清单，保护网关凭据 |
| 授予任务、外部 ID 映射、幂等收据与对账 | DTab Adapter | 保留业务事件，不重复承担实际 AI 扣款 |
| 工具试用次数和会员功能访问 | 对应 DTab/应用服务 | 不强行换算成 AI quota |

建议一个 DTab 用户映射一个 New API 内部用户；不同应用使用同一用户下可区分的凭据，共用额度。网关 Token 是调用凭据/限制，不是第二个钱包，不把用户提交的 user_id 当作可信归属。最终用户不需要在 New API 再注册、充值或获取自己的网关 Key。

“DTab 积分”是 quota 的产品显示单位。设置固定、版本化的 points_per_quota 换算，底层保留完整精度；不对每条低成本调用先四舍五入到 1 积分再扣一次。余额展示、报价和消费明细要能核对。精确汇率和积分包数值在真实成本测算后确定，不能静默改变已购额度的表示规则。

网关计算出的 quota/配置费用不等于供应商最终账单，更不等于平台收到的现金。成本尚未核对时标为估算；定期比对供应商账单、网关消耗和 DTab 订单，不拿一个余额差值当可靠结算。

### 5.1 映射目标

- 普通用户：daily subscription 对应少量每日积分；免费计划的有效期、续接、幂等和业务日要实测，不写成未验证的永久计划。
- 会员：daily subscription 对应较多每日积分；会员有效期与每日重置周期是两件事。
- 购买积分：wallet quota；会员到期后仍属于该用户，按可用功能消费。
- Group：仅作为受验证的模型/路由/计费配置；Group 本身不能代替 DTab 会员权益或每日订阅额度。

Free 与会员两套 daily 不能同时被无意叠加。也不能把所有用户放进一个共享网关账号，再相信浏览器的 user 字段实现多租户计费。

### 5.2 原版能力与待验收项

官方钱包文档确认周期重置与订阅/钱包计费偏好，但回退受活动订阅配置影响。[B01] 固定审查基线的 reset 函数按传入时间的 Location 计算下一日零点，不证明当前部署已正确配置业务时区。[B02]

此前审查的 Token 创建使用当前认证用户，订阅授予接口未展示 DTab 外部订单幂等键。[B03][B04] 因此自动开户、替用户发证、重复授予、防重放与对账都必须验证，不能宣称原版“完全即插即用”。优先受支持接口；只有确有缺口才评估有限补丁并保留上游更新路线。

## 6. 扣费与发放的一致性

### 6.1 发放

付款回调验签、核对商户/金额/币种 → DTab 订单确认 → 写持久授予事件 → 适配层调用网关 → 保存上游收据 → 标记发放完成。支付与发放分开，不能付款跳转回来就显示积分已到账。

同一订单只能得到一次有效授予。调用超时且不知是否已发放时进入 pending_reconciliation；先核对再重试。仅在 DTab 本地设唯一键不能证明远端操作 exactly-once。上游无稳定幂等/可核对收据时，阻止自动收费发放链路上线，不能盲重试或直写其业务表。

退款用补偿事件/上游受支持操作处理，保留原单与原授予；不删除记录、不对每日积分和购买积分进行无来源的统一加减。

### 6.2 调用

App 后端验证当前用户 → DTab 验证应用与操作权限 → 选择绑定该用户的网关凭据 → New API 预扣、调用、结算 → DTab 展示权威结果。

每日额度不足和购买积分的混合结算只由经验证的单一计费内核完成。异常后不能先在 DTab“补回余额”，稍后又接受网关退款，导致双退。跨日任务保留原预扣来源；昨日额度的迟到退款不能变成今日额外额度。网络断开、取消请求不自动代表供应商未执行，不盲目提交第二个有成本任务。

本地日志、任务完成状态、模型自报的费用都不是扣费成功凭据。消耗/退款至少关联 user_id、app_id、operation、网关用户/Token、请求/任务 ID、规则版本与实际状态。

### 6.3 不被 New API 支持的第三方 API

不能将普通去水印 API、任意 HTTP 服务直接当成 New API 原生可计费模型。可复用受支持的适配/任务插件时，先验证请求、usage facts、预扣/结算/退款；否则该积分处理模式暂不开放，或作为经成本确认的会员包含功能。

不为一个小工具在 DTab 再造一个 points_balance 扣费内核。若必须新增计费机制，先提交新的架构决策与统一账务方案，而不是偷偷使两个账本并存。

## 7. 大型独立应用：只固化相关边界

大型应用允许自定义域名、新窗口/标签页与独立容器部署；DTab Core 仍用单主域名。生产托管可在实际接入阶段验证 Railway/Northflank 等候选，不在当前 V1 增加服务费用或迁移 Core。

DTab 是统一登录/注册、会员和支付入口。独立应用没有有效 App Session 时返回 DTab，完成身份与操作权限检查后继续；已有合法应用会话可刷新/继续工作，不能把每个静态文件/API 请求都 302 回桌面。浏览器导航可重定向，未认证 API 返回适当错误；程序不通过 Referer 或“必须点击图标”证明授权。个人网址快捷方式不是受 DTab 控制的第三方网站，保持正常跳转。

统一入口不强制购买会员，不把应用“安装/添加到 Dock”当作扣费授权。鉴权交换、回调白名单、state/浏览器事务绑定、短时一次性凭据、防重放、会话撤销与深链安全在接第一个应用前另行验收；本文件不实现或宣称一个自制 launch code 就已达到 SSO 安全要求。

Infinite Canvas 保持独立仓库/服务及应用领域数据，通过小范围 Adapter 接入 DTab。关闭平台模式中的自有充值/扣点与绕过官方渠道路径，不能只隐藏按钮；不要删上游代码再大规模重写。上游检测 → 更新 PR → 隔离预览/测试 → 人工批准 → 固定版本/镜像发布；不把更新流水线或 Fork 写成此次已创建。

不在当前 V1 启用第三方任意可执行上传。大型官方受管应用不是开放商店沙箱的替代品，许可证与修改源码义务另行审查。

## 8. 实施分期与验收

保持 05 文档的 M0–M5 顺序不变。当前仅更新合同、展示规则和任务。支付开关默认 false；AI 网关/积分包、外部应用各自需独立启用，未接通时隐藏购买入口，不用 mock 余额宣称生产可用。

- V1 本地/页面开发：统一免费/会员展示、入口与权益契约；保持现有免费能力和数据，不部署 New API。
- 商业化阶段（M5-P）：一个会员及真实支付/发放验证。AI 未交付时不可把每日积分当作已可用权益收费宣传。
- AI PoC：独立 New API 测试实例，两个测试用户、每人两个应用凭据，验证 daily + wallet；无真实供应商凭据时标 blocked。
- 收费开放：只有对应支付、网关、媒体、安全与 B gates 全部通过后，按用户确认的价格启用。

| 验收 | 必须得到的结果 |
| --- | --- |
| B01 | 用户侧只有一个付费会员；月/年不是两级；无 Max 或工具单品买断入口 |
| B02 | 普通工具包含在会员中不扣分；付费处理在提交前明确积分规则 |
| B03 | 普通已登录用户可以买积分使用可用 AI，无强制先购会员 |
| B04 | 业务日每日仅重置一次，不累积；时区、客户端跨区、断网恢复与前端 next_reset_at 一致 |
| B05 | 购买积分不被每日重置、会员到期、取消续费或删除 Dock 入口清除 |
| B06 | 实测每日不足时的跨池预扣和最终差额补扣；不能只验证余额完全耗尽后的整笔回退 |
