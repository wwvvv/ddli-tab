# GoTab → DTab OS V1 渐进迁移方案

版本：1.0 · 2026-09-16

基线：`a3f2a2b8510fb8178ab9c0fdd2d65a19585c8a51`（main，审查时 HEAD）。

目标：保留旧数据与行为参考，建立源码可控的 OS 主屏幕和平台模块；每阶段可验证、可回退。不修改授权事实，不假设当前仓库包含作者另外交付的完整源码。

## 2. 不做的迁移方式

禁止批量改压缩 bundle、继续通过文案找 DOM 注入商店/相册；禁止从头编造一个“GoTab Engine”并声称复用全部拖拽源码；禁止仅换 Next.js package.json 后覆盖整个工程。

禁止把原 `/web` 复制到 `/legacy/` 就称迁移完成：原代码包含 `/assets`、`/api`、root SW 等绝对路径，必须逐项重定位或以旧部署回滚保留。

不做 root 主屏幕和 iframe 旧桌面同时持有可写状态的套壳。可以参照旧 UI 做行为测试，但两套运行时不能同时写同一个 Redux/IndexedDB/snapshot。

“保留 40%/重写 60%”之类未度量百分比不作为预算依据。按依赖、数据风险与验收阶段估算，不用代码行比例替代实施计划。

## 3. 冻结与分支规则

本次只提交规格，不改变运行路径。实施从同步后的 main 建工作分支，例如 `feat/os-v1-m0`，每阶段独立提交/PR。不要 reset --hard、git clean 或覆盖本地未提交改动。

记录开始时 commit、tree、Node、包管理器、构建命令、现有浏览器截图、旧导入导出样例与基线 SHA 清单。保留 `legacy/gotab/LICENSE` 和完整上游归属，不将授权文件/商业合同擅自公开。

`legacy/gotab/web` 原文件保持不变；必要的 SW/路由兼容改动放在 src/local 和构建脚本的受审补丁中，更新已有 baseline 清单。旧配置与原包可从 Git 基线回滚，不必复制多个混乱版本。

有完整授权前端源码时，应先确认可以构建和测试，再决定复用哪些模块；没有时使用当前适配层作为过渡和迁移来源，不以反编译代替稳定源码工程。

## 4. 阶段 M0：盘点、复验、平台探针

交付物：`docs/dtab-os-v1/implementation/M0-BASELINE.md` 与 `M0-COMPATIBILITY.md`（由实施者实际生成，不提前填通过）。

复验旧构建、单测、扩展构建、浏览器回归、数据库权限测试。测试环境缺失或网络/账户失败逐项记录；不能跳过后报告全绿。

最小 Next.js 探针验证：页面、Route Handler、cookie、Supabase 会话刷新、RLS、请求体边界、媒体 GET/HEAD、404 与深链刷新。查阅 EdgeOne 实际适配与函数环境，不凭本地 `next dev` 判断生产能力。

ImgBed 探针使用独立测试目录，验证当前版本、允许渠道、实际 Token 权限、普通/分片上传、缩略图开关、匿名读取及删除。输出脱敏证据，不记录 token。无法取得真实环境时，门槛标记 blocked，独立本地开发可以继续，但不能开放受影响功能。

退出门槛：有可重现基线；新技术组合已选定并明确哪些平台能力仍待实测；不能把远程源码内容读取当作执行过测试。

## 5. 阶段 M1：源码壳与根路由兼容

### 5.1 先处理旧 Service Worker

现有 SW 使用 `/ddli-local-sw.js` 且作用域为 `/`。浏览器可能长期受旧缓存控制，即使服务器已部署新页面也会返回旧 HTML。

必须提供一个仍在相同 SW URL 下可更新的兼容版本：

- 将本地 API 模拟从宽泛的 `/api/*` 改为已清点的旧接口允许列表。
- 对 `/api/v1/*`、`/os/*`、Next 内部资源、认证、私有媒体和管理请求明确放行到网络，不参与旧缓存和导航兜底。
- 导航兜底只用于明确的旧入口，未知路由不能返回旧 index.html。
- 新缓存名称采用 `dtab-os-*`，旧缓存清理只能删除本应用已知旧版本，不能删除整个 origin 的其他缓存。
- 更新激活前提示保存状态；确认后接管/刷新。测试等待激活、旧 tab 未关闭、离线重连和更新失败，不默认强行 skipWaiting 导致在途事务丢失。

还需修改服务器通配 rewrite：新 Next 路由/API 必须优先于旧 SPA fallback；不能把 `/api/v1/*` 的 404 变成 200 HTML。

### 5.2 新壳暂置 /os

新主屏幕在 `/os`，商店/相册/设置在 `/os/store` 等子路径；旧 `/` 保持原样。这是同一个产品域名里的过渡，不新增用户/管理员子域名。

Next.js 与旧静态资源组合必须在 EdgeOne 实测。新壳不嵌套有独立存储写入的旧页面；普通用户旧数据仍在旧路径，测试用户显式执行导入。

默认 app 注册表建立 store、gallery、settings。相册在隐私/上游未通过前可以显示明确的开发状态，但不能作为已可用线上功能推广。

### 5.3 包管理器迁移

M0 仍按原 npm 工程执行。M1 在一个可回滚提交中引入 pnpm workspace，保留 legacy 构建和测试命令的功能，更新 CI/本地教程/部署安装命令并验证。不要只删除 package-lock，不运行验证。

迁移期间可以保留旧 lock 的 Git 基线作为回退，但同一工作树最终只认一个活动 lockfile。对仍未迁移的独立工具应显式隔离，不能两个包管理器同时管理同一根依赖图。

退出门槛：旧版仍可用；新 /os 可访问和刷新；新 API 不被旧 SW 吞掉；完整构建/资源路径可验证。

## 6. 阶段 M2：本地桌面与数据转换

先完成标准网格、添加、网址/文件夹/组件、Dock 和本地图标；再转换旧数据。纯函数与组件测试不得依赖上游在线服务。

### 6.1 转换输入

支持已知旧导出 JSON、同源本地已知版本数据、旧云快照的显式导入。仅从可验证数据结构读取，不在新 UI 动态 import 旧 hashed bundle；需要借旧导出函数时限定在迁移工具/旧版上下文，不能作为长期依赖。

第一次读取前导出原始备份，写入 migration receipt；receipt 包含旧数据摘要 hash、目标 schema、迁移版本、数量统计与状态，不包含 token。

### 6.2 映射表

| 旧数据 | 新数据 | 不支持项处理 |
| --- | --- | --- |
| link card | Shortcut Entity + Placement | 原名/URL/图标保留，非法 URL 标记不可打开，不执行 |
| listData 顶层分组 | 桌面 Page | 保留名称、顺序与原 ID 映射 |
| 旧文件夹 | Folder + 子 Placement | 深层嵌套先报告，不能随意展开丢层级 |
| dockListData | Dock Placement | 只有确证同一对象才共享 Entity；不同同名/同 URL 个性化不强合并 |
| freeDragListData | legacy layout 快照/迁移附属数据 | 不会排布时给出预览和提示，保留原始坐标 |
| component card | Widget 实例 | 未移植组件保留配置、显示不可用占位，不删掉 |
| wallpaper/settings | 有界设置字段 | HTML/脚本字段作为原始备份保留，禁止插入新 DOM |
| image URL/icon | IconRef | 外链不伪装成已上传资产；data/blob URL 单独核验迁移 |
| note 等业务内容 | 对应可支持模型或 legacy archive | 不因首版没功能静默丢弃 |

### 6.3 幂等与验证

相同源 hash + 迁移版本重复执行不得重复生成桌面。ID 映射固定且可复现；预览给出分组/卡片/组件/图标数量、未知字段、失败项。用户确认后，单个 Dexie 事务提交目标数据、初始化标识和 receipt。

异常中断、配额不足、schema 不符、引用循环必须可安全退出，旧数据不变。数量核对通过仍不代表布局语义等价，需代表性截图和交互验收。

禁止在成功之前删除 localStorage、旧 IndexedDB、legacy 云快照或旧备份。新 schema 不向旧表双写；否则回滚时会产生难以修复的双主冲突。

退出门槛：A01/A03/A04/A05/A08 通过；已登录用户导入不会覆盖更近的云端数据。

## 7. 阶段 M3：账号、新同步与官方预设

用现有认证/错误处理思路，但创建明确的新设置 UI。切换账号必须清空旧用户内存与订阅，队列绑定 OwnerKey；共享浏览器不能把上一人的相册列表当下一人的缓存。

新 snapshot/document 协议、RLS 与 RPC 独立迁移。保留旧 sync-engine 的可复用纯逻辑与测试，重写与 Redux/压缩导出绑定的 adapter。并发、删除与编辑、整页排序、请求重试和重复 requestId 都需要测试。

官方预设由独立编辑模式生成；写入不可变版本后原子切换 active version。服务端账号初始化要检查真实 cloud initialized 状态，游客本地初始化不能抢先覆盖已有账号。

旧版本自动同步暂停/停用与新同步启用须有明确交接；不得在两个界面同时连接同一个可写数据模型。

退出门槛：A02/A07/A12 通过；真实邮件/会话恢复/双设备与数据库权限验收记录存在。

## 8. 阶段 M4：官方商店、图标与相册

先实现 Product 与 App Registry 的对应、免费获取/移除、网页资源添加和主题应用。应用代码只从仓库部署；管理端不能上传执行包。

官方组件逐项完成依赖审计；不可用上游组件不能仅改成“官方内置”就上架。

用户图标上传接 ImgBed 并形成正确的资产归属与引用。媒体链路完成小文件限制、权限旁路检测、上传登记失败恢复、引用删除与幂等清理后，再开放相册。

隐私失败不影响继续开发本地桌面，但阻止云相册公开。平台能力不足时写清楚失败证据，不能暗改用户要求成公开图床/自带存储/新增 VPS。

退出门槛：A06/A10/A11 通过；实际私有文件读取与缩略图链路验收，不只验证 API 列表权限。

## 9. 阶段 M5：后台、离线、扩展与正式切换

后台补齐预设编辑/发布、官方商品、用户状态与审计。新扩展保持最小 activeTab 权限，使用版本化消息契约与 origin 验证；不能用模拟网页桥验收代替真实浏览器扩展授权完整链路。

正式离线壳与 Next 路由缓存分离；测试用户 A 退出后 B 不获得 A 的旧 HTML/API/媒体缓存。新 SW 接管、旧 tab、首次安装、版本升级、回滚各有用例。

只有核心功能和所有数据/安全门槛通过后，才在独立发布提交把新主屏幕从 /os 切为 /。公开 /os 旧深链有重定向/兼容；旧根构建的回滚产物仍保留。

不是把旧站简单搬去 /legacy；如要长期可访问旧站，必须另做路径重定位验证。未做完时，回退使用已保存旧部署版本与旧数据快照，而不是一个未经测试的目录。

支付是独立开关阶段：没有真实支付服务与验签测试就保持 false，不阻挡免费桌面 beta，但不能卖未验收的云能力。

退出门槛：A09/A13/A14/A15/A16 通过；新旧行为差异有清单；用户数据恢复演练与部署回滚演练有证据。

## 10. 回滚设计

分为三类，不能混用：

1. UI/部署回滚：切回上一已验证产物，并同步恢复对应 SW 版本策略；旧缓存不能永久劫持新/旧路由。
2. Schema/数据回滚：V1 采用向前兼容、只新增表/列；旧数据始终保留。不能直接 DROP 新表来“恢复旧站”。
3. 用户内容回滚：用户选取迁移前/重置前备份恢复。新 OS 中新增的内容旧版未必能理解，必须先导出新 OS 备份和可兼容的书签子集，告知不支持项，不能声称自动无损反向转换。

回滚也不能自动覆盖期间新产生的照片、订单和权益；这些业务与桌面 payload 分离。
